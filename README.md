# Lovely | Next.js + Tailwind + Supabase + shadcn/ui

حزمة مصدر قابلة للتشغيل، إصدار 0.14.0، مبنية من الصفر على وثيقة متطلبات أتيليه وتأجير فساتين بتاريخ 21 نوفمبر 2026.

**هذه مرحلة أولى، وليست نظام إنتاج مكتملًا.** لا تستخدم بيانات عملاء أو مدفوعات حقيقية قبل استكمال الربط والسياسات واختبارات القبول. هذه حزمة مصدر؛ الربط والنشر واختبارات الخدمة المستضافة تُدار منفصلًا عنها.

## التشغيل السريع

المطلوب: Node.js 22.x، وnpm.

```bash
npm ci
npm run dev
```

افتح `http://localhost:3000`.

- `/`: كتالوج عربي RTL. يعرض بيانات تجريبية صريحة إذا لم تضف إعدادات Supabase.
- `/dresses/sage`: مثال تفاصيل فستان في وضع عدم الربط.
- `/demo`: مساحة استعراض منفصلة ببيانات وهمية، تشمل لوحة اليوم والفساتين والحجوزات والتقويم والعملاء والتنبيهات وملخصًا ماليًا تجريبيًا.
- `/login`: دخول حقيقي عبر Supabase بعد إعداد الخدمة، ومعطّل بوضوح قبل ذلك.
- `/workspace`: مساحة حقيقية محمية، تتيح قراءة المخزون والحجوزات المصرح بها، وإضافة وتحرير وأرشفة الفساتين ورفع صورها والتصنيفات للأدمن. ليست نفس شاشة الاستعراض.

إنشاء الحجز داخل `/demo` محاكاة داخل ذاكرة الصفحة فقط. تحديث الصفحة يمسح التغييرات. تغيير الدور للمعاينة ليس آلية صلاحيات. أسماء العملاء والأرقام والفساتين والإحصاءات تجريبية. الرسومات أصلية مبدئية وليست صور منتجات حقيقية. تاريخ مساحة الاستعراض ثابت: السبت 5 ديسمبر 2026.

## الأدوات المستخدمة

- Next.js App Router وTypeScript.
- Tailwind CSS v4.
- مكونات shadcn/ui فعلية، مبنية على Base UI في الإصدار الذي تم تثبيته.
- Supabase Auth وPostgreSQL وStorage، مع `@supabase/ssr`.
- Zod للتحقق على الخادم، وPlaywright لاختبارات المتصفح.

الإصدارات الدقيقة في `package-lock.json`. استخدم `npm ci` لإعادة نفس التثبيت. لم تُستخدم صور منتجات خارجية.

## ربط مشروع Supabase جديد

1. أنشئ مشروعًا جديدًا تحت حسابك وحدد المنطقة وخطة التكلفة بنفسك. لم تُنشأ موارد مدفوعة بالنيابة عنك.
2. انسخ `.env.example` إلى `.env.local` على جهازك، وأضف عنوان المشروع و**Publishable Key** فقط. لا تضع `service_role` أو مفتاحًا سريًا في أي متغير `NEXT_PUBLIC_`، ولا تشارك كلمة مرور قاعدة البيانات في المحادثات أو Git.
3. نفّذ الملفات الاثني عشر داخل `supabase/migrations/` بترتيب أسمائها: `202611220001_foundation.sql` ثم `202611220002_inventory.sql` ثم `202611220003_booking_forms.sql` ثم `202611220004_optional_payment_method.sql` ثم `202611220005_admin_dashboard.sql` ثم `202611220006_notifications.sql` ثم `202611220007_manual_late_fees.sql` ثم `202611220008_category_management.sql` ثم `202611220009_collision_notifications.sql` ثم `202611220010_handover_return.sql` ثم `202611220011_receipt_reports.sql` ثم `202611220012_image_ordering.sql`، عبر SQL Editor للمشروع الجديد. لا تطبقه على مشروع قائم دون مراجعة: يضبط منح الوصول داخل `public` ويحتاج صلاحيات مالك القاعدة.
4. عطّل التسجيل العام من إعدادات Supabase Auth. أنشئ أول حساب أدمن من لوحة Authentication، ثم أضف سجل `profiles` المطابق لمعرف حسابه، من SQL Editor فقط:

```sql
-- استبدل المعرف بمعرف الحساب الحقيقي من لوحة Authentication.
insert into public.profiles(id, full_name, role)
values ('AUTH_USER_UUID_HERE', 'اسم المدير', 'admin');
```

5. حسابات الموظفين تُنشأ حاليًا من لوحة Authentication ثم يضاف لها سجل `profiles` بالدور `employee`. واجهة إدارة المستخدمين لم تُنفذ بعد. اجعل `active=false` لتعطيل الموظف بدل حذف سجله التاريخي.
6. أعد تشغيل التطبيق. ادخل من `/login`، وأضف تصنيفًا ثم فستانًا من `/workspace`. يبدأ الفستان بحالة غير متاح. افتح اسم الفستان من المخزون لتحريره ورفع صوره، وراجع رابط الأرشيف لاستعادة فستان مؤرشف.
7. تأكد من اختبار الصلاحيات بحساب أدمن وموظف وزائر على مشروع اختبار، خصوصًا Auth وStorage في الخدمة الحقيقية. اختبارات PostgreSQL المحلية لا تثبت تكامل الخدمة المُستضافة.

الـ Storage bucket المسمى `dress-images` متاح لصور الكتالوج برابط مباشر. لا ترفع فيه أي هوية أو بيانات عميل أو مستند خاص. رفع الصور محصور بالأدمن على مستوى RLS. أرشفة فستان لا تسحب صورة سبق نشر رابطها من كاش أو من شخص احتفظ بالرابط. واجهة رفع الصور متاحة للأدمن بعد الربط. تتحقق من الملف وتعيد ترميزه WebP وتزيل EXIF. حذف الصور وترتيبها يدويًا لم يُنفذا بعد.

## السياسات غير المحسومة

كل التغييرات المالية والتشغيلية داخل العرض غير حقيقية. إنشاء الحجوزات الفعلية في قاعدة البيانات متوقف افتراضيًا عبر `settings.live_bookings_enabled=false`، وتحتاج حقول السياسة إلى اعتماد صريح. **لا تغيّرها لمجرد تشغيل العرض**.

راجع `docs/DECISIONS.md` قبل التشغيل. لم نفعّل الاحتفاظ بالبطاقة الشخصية، ولم نخزن رقمًا أو صورة لهوية. الإلغاء والاسترداد وتعديل السعر/التاريخ والتسليم والاستلام تحتاج قرارات وتنفيذًا لاحقًا.

توجد واجهات إنتاج لإنشاء الحجز والمقدم وتسجيل الدفعات عبر RPC، محكومة بإعدادات التشغيل. لا يوجد دفع إلكتروني أو بوابة تحصيل.

## الاختبارات

```bash
npm run lint
npm run typecheck
npm test
npm run test:db
npm run build
npm run test:e2e
```

- `npm test`: اختبارات قاعدة يوم التجهيز، أول موعد لاحق، التواريخ وحساب القروش دون أخطاء الكسور العائمة.
- `npm run test:db`: يشغّل PostgreSQL مؤقتًا على المنفذ 55439 باستخدام `embedded-postgres`، ثم يختبر المهاجرة وRLS والمعاملات. لا يتصل بأي مشروع سحابي. schemas الخاصة بـ Auth وStorage ممثلة محليًا، وليست خدمة Supabase الحقيقية. يتطلب السماح بتثبيت حزمة PostgreSQL الأصلية لنظامك، وتشغيله كمستخدم غير root.
- `npm run test:e2e`: بعد `build`، يشغّل التطبيق ويختبره في Chrome. على Linux يستخدم `/usr/bin/google-chrome` افتراضيًا. يمكنك ضبط `CHROME_PATH`، أو تعديل `playwright.config.ts` لاستخدام Chromium المثبت عبر Playwright.
- صور المعاينة الفعلية في `evidence/`. تقرير التحقق في `docs/VERIFICATION.md`.

## الأمان في هذه المرحلة

- السعر الاسترشادي في جدول منفصل `dress_prices`، وليس عمودًا مخفيًا بالواجهة فقط.
- الزائر لا يملك الوصول إلى العملاء والحجوزات والمدفوعات والسجل.
- الموظف يرى الحجوزات التي أنشأها أو أُسندت له فقط. هذا قيد احترازي مؤقت حتى اعتماد نطاق عمل الموظفين، وليس قرارًا نهائيًا عن طريقة تشغيل الأتيليه.
- لا يستطيع المستخدم تعديل دوره. قراءة السعر الإداري والمالية العامة وسجل النشاط للأدمن فقط.
- منع التعارض في PostgreSQL بقيد `EXCLUDE`، وليس بفحص واجهة فقط.
- المدفوعات بالقروش الصحيحة، لا يُقبل دفع يتجاوز المستحق، ولا يوجد حذف مباشر للدفعات أو السجل عبر أدوار التطبيق.
- قيود قاعدة البيانات لا تعني أن اختبارات الأمان الكاملة انتهت. مطلوب اختبار اختراق وصلاحيات على Supabase قبل الإنتاج.

## ما يأتي بعد هذه الحزمة

راجع `docs/IMPLEMENTATION.md` للتفريق بين المنفذ، والتجريبي، وغير المنفذ. أهم المراحل التالية: اعتماد السياسات، إنشاء وربط بيئة اختبار، استكمال حذف الصور وترتيبها وإدارة التصنيفات، إدارة الموظفين، ربط الحجوزات والمدفوعات الفعلية، التسليم والاستلام والفحص، التنبيهات المشتقة من الواقع، تقارير مالية حقيقية وتصدير آمن، النسخ الاحتياطي وتجربة الاستعادة، ثم النشر على Vercel تحت حساب المالك.

اعتُمد اسم Lovely وشعار المالك وألوان الوردي/الأسود/الأبيض. صور الفساتين مولدة للمراجعة وليست مخزونًا حقيقيًا. لا يوجد حجز ذاتي للزائر، أو QR، أو تأمين مالي، أو نظام صيانة مستقل.

## وضع النموذج الاختباري

اضبط `ATELIER_PROTOTYPE_MODE=true` في بيئة البناء والتشغيل معًا. يظهر تحذير ثابت في كل الصفحات بأن النسخة اختبار فقط وغير مكتملة وغير مخصصة للتشغيل التجاري أو استقبال العملاء. يمنع هذا الوضع حفظ الحجوزات والدفعات في إجراءات الخادم، حتى لو تغير إعداد القاعدة بالخطأ. احتفظ أيضًا بـ `live_bookings_enabled=false`، ولا تدخل أسماء أو هواتف أو معاملات فعلية. هذا الوضع ليس بديلًا عن حماية كل روابط النشر والتحقق من شروط خطة الاستضافة. لا يُرفع القيد للتشغيل التجاري دون استكمال الدورة والاختبارات والقرارات والاشتراك الملائم.

وضع الاختبار هو الافتراضي الآمن إذا غاب المتغير أو كُتب بشكل غير صحيح. القيمة الصريحة `false` وحدها تزيل قيد النموذج الاختباري؛ لا تستخدمها في نشر هذه النسخة التجريبية.

غرامة التأخير اختيارية، لا تُحسب مع كل تأخير. للأدمن فقط زر داخل تنبيه حجز متأخر مسجل خارج الأتيليه، مع مبلغ وسبب وتأكيد صريح. المهاجرة السابعة تضيف `add_late_fee` وتمنع الإدراج المباشر للغرامات من حسابات التطبيق. تستخدم معرف طلب ثابتًا للمحاولة وإعادتها، وقفل الحجز قبل الإضافة. يتغير المستحق فقط، ولا تُسجّل الغرامة كدفعة ولا يُرسل طلب مالي للعميل ولا يُخصم مال إلكترونيًا. تبقى الإضافة معطلة في وضع النموذج الاختباري، و`live_bookings_enabled=false` كما هو. عرض تفاصيل الحجز يبين مبلغ كل غرامة وسببها.

حُسم أيضًا أن إتمام العودة يحتاج سداد المتبقي كله. هذا قرار للمرحلة التالية، وليس ادعاء بأن إجراء العودة اكتمل في هذا الإصدار. فحص العودة المعتمد سليم/يحتاج صيانة، مع تعدد الإكسسوارات/السوستة/الخياطة/القطع دون صور. الضمان ومعالجة تعارض العودة المتأخرة مع الحجز التالي ما زالا بحاجة إلى قرار؛ لا تعديل أو إلغاء تلقائي للحجوزات.

## تحديث 0.10.0

إدارة التصنيفات للأدمن في `/workspace/categories`: إضافة، تعديل الاسم، وحذف التصنيف غير المستخدم بعد تأكيد. لا يمكن حذف تصنيف يرتبط بأي فستان، حتى المؤرشف. المهاجرة الثامنة تضيف رقم نسخة لحماية التعديل والحذف من التغييرات المتزامنة، وتفرض تعديل/حذف التصنيف عبر RPC للأدمن فقط. الحذف لا يحذف فساتين أو حجوزات، وكل تغيير محفوظ بسجل النشاط. لم تُضف أزرار تفعيل/إخفاء أو تُحسم سياسة عرض الزائر. `/demo/categories` معاينة صريحة معطلة الحفظ.

قرار التأخير الجديد: عند تأثيره على الحجز التالي يظهر تنبيه مهم للأدمن فقط، دون حظر تسليم آلي بسبب التعارض، ودون إلغاء أو تحريك تلقائي. قواعد إنشاء الحجوزات ويوم التجهيز تبقى كما هي. هذا القرار موثق هنا؛ تنبيه التعارض نفسه ودورة التسليم والعودة لم تُنفذ بعد في هذا الإصدار.

## تحديث 0.11.0

بداية تنفيذ التنبيه المهم المعتمد: حجز متأخر ما زال بحالة خارج الأتيليه، وله حجز تالٍ لنفس الفستان اقترب إلى اليوم التالي أو بدأ بالفعل. يظهر للأدمن في أول المركز، بلون وحدّ وعنوان مميز، ورابط أقرب حجز متأثر وموعده، وصفحة `/workspace/notifications/collision`. لا تغيير لأي موعد أو مبلغ أو حالة حجز، ولا حظر تسليم آلي بسببه. القراءة محفوظة ولا تخفي سببًا نشطًا. المهاجرة التاسعة مطلوبة.

هذا الإصدار يرصد الحالة بينما الفستان لا يزال مسجلًا خارج الأتيليه. إجراء العودة الفعلية وسجل يومها لم يُنفذا بعد؛ يلزم ربط أثر العودة المتأخرة وفترة التجهيز الفعلية بهذا التنبيه عند تنفيذ ذلك الإجراء. لا يُعد هذا إكمالًا لكل حالات التأخير أو دورة التسليم والعودة. المعاينة المنفصلة تعرض أربع بطاقات الآن، لا ثلاثًا، ومرجع اليوم الثابت كما هو.

توضيح قرار التسليم الأحدث: يدفع العميل المقدم عند التسليم، ولا يُشترط سداد الرصيد كله قبل الخروج. سداد الرصيد كله شرط لإتمام العودة، كما سبق تأكيده. ذكر المالك البطاقة القومية كضمان؛ وأكد تسجيل حالة استلام/رد فقط دون رقم أو صورة؛ يدفع العميل الباقي وقت الاسترجاع ويستلم البطاقة حينها. لم تُضف حقول هوية أو صور أو مسح مستندات، ولا يُعد ذلك اعتمادًا قانونيًا للاحتفاظ بأصلها.

## تحديث 0.12.0: Lovely والتسليم والعودة

هوية Lovely في الكتالوج والهيدر والفوتر والأيقونة والدخول ونوافذ التشغيل والتقويم والتصنيفات والمالية والتنبيهات. الشعار من صورة المالك نفسها، مع نسخة WebP محسنة دون بيانات وصفية. الوردي الداكن للأزرار المقروءة، الوردي الفاتح للخلفيات، وأسود/أبيض للنصوص والمساحات. لا تبديل لألوان الفساتين نفسها. راجع `docs/BRANDING.md`.

المهاجرة العاشرة تضيف سجل تسليم وسجل عودة منفصلين، بقراءة حسب صلاحية الحجز ودون تعديل/حذف مباشر. التسليم يتطلب مقدمًا مستلمًا مسجلًا وتأكيد استلام الضمان وجاهزية الفستان، لا سداد الرصيد كله. العودة تتطلب تسوية الرصيد كاملًا شامل أي غرامة اختيارية، ورد الضمان وفحص سليم أو صيانة متعددة الخيارات المعتمدة. لا رقم/صورة بطاقة، ولا صورة فحص أو نص هوية حر. المعاملات مقفلة على الحجز وآمنة عند إعادة نفس الطلب؛ تغيير محتوى طلب محفوظ مرفوض.

أيام الخروج والرجوع الفعلية تُسجل بيوم مصر الحالي، دون إعادة كتابة المواعيد المخططة أو backdating. التسليم داخل أيام الحجز المخططة فقط؛ التمديد/التعديل يحتاجان القاعدة المعتمدة لاحقًا، لا تغييرًا تلقائيًا. الحجز القديم الذي حالته خارج لكن لا يملك سجل تسليم لا يُمنح تأكيد ضمان تاريخي مفترض؛ يمكن للموظف المصرح تسجيل العودة ورد الضمان الآن بالتحقق الفعلي.

بعد العودة يتحدد أول يوم بعد التجهيز بـيوم الاستلام المسجل + ٢. يحترم إنشاء حجز جديد هذا التاريخ، وكذلك اقتراح الإتاحة. لا تُلغى أو تُحرك الحجوزات الموجودة؛ تنبيه التعارض المهم يستمر بعد العودة المتأخرة أثناء نافذة تأثير التجهيز، وليس فقط أثناء حالة خارج. يعرض أقرب حجز متأثر. تأكيد انتهاء التجهيز والصيانة إجراء يدوي بعد اليوم الكامل، لا تشغيل صيانة مستقل ولا تسعير إصلاح. لا يحول تنبيه التعارض نفسه إلى حظر تسليم آلي، ويؤكد الموظف الجاهزية الفعلية عند التسليم.

`/demo/workflow` معاينة معطلة الحفظ لأربع حالات. في صفحة الحجز الفعلية نفس المكونات مربوطة بإجراءات الخادم، مع قيد مستقل على prototype mode. كل الحفظ التشغيلي والمالي المذكور يظل معطلًا في النسخة الاختبارية، وgate القاعدة يظل false. معاينات المتصفح والاختبارات المحلية ليست اختبار جلسة موظف مستضافة مكتملًا.

المتبقي للإصدار الكامل يشمل إدارة الموظفين بالواجهة، التقارير/التصدير، حذف/ترتيب الصور، قواعد التعديل/الإلغاء/الاسترداد، مراجعة نطاق الموظفين ومطابقة العملاء، اختبار النسخ الاحتياطي والاستعادة، والقبول الكامل على البيئة المستضافة. تقويم العمليات الحالي يوضح التجهيز المخطط؛ يوم الاستلام والتجهيز المسجلان يظهران في تفاصيل الحجز والتنبيه. لا يُقدّم هذا التحديث كإنهاء لكل المشروع.

## تحديث 0.13.0: دفتر القبض وCSV

`/workspace/reports` للأدمن فقط، مع فترة صريحة بيوم مصر، ومجموع/count لحركات القبض المسجلة في الفترة ومعاينة أول ٢٠ حركة. التنزيل `/workspace/reports/download` يقرأ دفتر الفترة كله من جديد، ويطابق عدد الصفوف ومجموع القروش قبل إنشاء CSV. إذا زادت الحركات عن ٥٠٠٠ أو الفترة عن ٣٦٦ يومًا، يرفض مع طلب تضييق الفترة، لا ملفًا ناقصًا. يوضح التقرير أن وقت الدفعة هو أساس الفترة، وليس يوم الحجز، وأن المبلغ المستلم ليس ربحًا أو غرامة غير محصلة.

CSV عربي UTF-8 مع BOM، اقتباس/هروب للفواصل والأسطر وعلامات الاقتباس، حماية من صيغ الجداول، وحفظ الهواتف/الأكواد كنص لمنع فقد صفر البداية. المبالغ عشرية دقيقة مشتقة من قروش صحيحة دون float. يحتوي الملف الحقيقي بيانات عميل، فلا يرسل لأحد تلقائيًا، ويُقدّم بـprivate/no-store للأدمن فقط. لا تعديل مدفوعات أو حجوزات أو gate. المهاجرة ١١ تضيف RPC قراءة ومؤشرًا فقط. `/demo/reports` وتصديره يستخدمان سجلين مصطنعين منفصلين بوضوح، لا بيانات بيئة المراجعة المستضافة.

قرار الإلغاء الجديد: المقدم غير مسترد عند الإلغاء. لم تُحدد قاعدة مبالغ تتجاوز المقدم أو رسوم إلغاء إضافية؛ لم يُنفذ إلغاء/رد تلقائي ولا إجراء على مال عميل ضمن هذا التحديث. بقية تقارير الحجوزات/الموظفين التفصيلية إن لزمت لا تُدّعى مكتملة بهذا الدفتر.

## تحديث 0.14.0: ترتيب الصور والصورة الرئيسية

في إدارة الفستان، للأدمن تقديم/تأخير الصور محليًا ثم حفظ القائمة كاملة؛ أول صورة هي الرئيسية في الكتالوج والتفاصيل. الموظف يرى الصور فقط. الحفظ معطّل في المعاينة ولو تحرك ترتيبها المحلي؛ التغيير غير المحفوظ مُسمى بوضوح. صور المعاينة الثلاث لنفس الفستان المصطنع، صورتان منها قصّات تفاصيل من الأصل نفسه، لا فساتين مختلفة ولا زوايا مخترعة.

`reorder_dress_images` يقفل الفستان ويتحقق من كامل مجموعة صور الفستان والنسخة، ويرفض التكرار/صورة أجنبية/نقص أو زيادة القائمة. لا تحديث مباشر للترتيب من حسابات التطبيق. طلب محفوظ بالفعل لا يكتب أو يكرر سجل التدقيق، حتى عند إعادة النسخة القديمة. الترتيب المختلف بنسخة قديمة يُرفض بدل الكتابة فوق تعديل أحدث. الصورة المضافة تُلحق في النهاية تحت قفل الفستان، فتأخذ الرفعات المتزامنة مواضع مختلفة، وترفع نسخة الفستان بعد الإدراج الناجح فقط. لا تغيير لأي صف موجود بمجرد المهاجرة ١٢، ولا إعادة ترتيب أو إضافة إلى بيانات المراجعة المستضافة.

تُمسح نسخ صفحات الكتالوج/التفاصيل والإدارة بعد الحفظ، وتبقى رسالة نجاح الترتيب في المكون الأب حتى إن أعيد تحميل قائمة الصور. يجب حفظ تعديلات بيانات الفستان غير المحفوظة قبل ترتيب الصور؛ تعديل الصور يحدّث النسخة المشتركة. حذف الصور وملفات التخزين ليس ضمن هذا التحديث، ولم يُعرض له زر حفظ وهمي.

لتمييز العرض الثابت عن البيانات المحفوظة، تنبيه المعاينة يضم رابطًا واضحًا إلى `/workspace` بعنوان دخول الفريق. هذا لا يلغي المصادقة ولا يفعّل أي gate. أُزيلت عبارة قديمة في معاينة إدارة الصور توحي أن القاعدة غير مربوطة؛ المعاينة ليست شاشة البيانات المتصلة.
