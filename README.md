# أتيليه | Next.js + Tailwind + Supabase + shadcn/ui

نسخة تأسيسية قابلة للتشغيل، إصدار 0.3.0، مبنية من الصفر على وثيقة متطلبات أتيليه وتأجير فساتين بتاريخ 21 نوفمبر 2026.

**هذه مرحلة أولى، وليست نظام إنتاج مكتملًا.** لا تستخدم بيانات عملاء أو مدفوعات حقيقية قبل استكمال الربط والسياسات واختبارات القبول. لا يوجد نشر أو مشروع Supabase مُنشأ ضمن هذه الحزمة.

## التشغيل السريع

المطلوب: Node.js 22 أو أحدث، وnpm.

```bash
npm ci
npm run dev
```

افتح `http://localhost:3000`.

- `/`: كتالوج عربي RTL. يعرض بيانات تجريبية صريحة إذا لم تضف إعدادات Supabase.
- `/dresses/sage`: مثال تفاصيل فستان في وضع عدم الربط.
- `/demo`: مساحة استعراض منفصلة ببيانات وهمية، تشمل لوحة اليوم والفساتين والحجوزات والتقويم والعملاء والتنبيهات وملخصًا ماليًا تجريبيًا.
- `/login`: دخول حقيقي عبر Supabase بعد إعداد الخدمة، ومعطّل بوضوح قبل ذلك.
- `/workspace`: مساحة حقيقية محمية، تتيح قراءة المخزون والحجوزات المصرح بها، وإضافة وتحرير وأرشفة الفساتين ورفع صورها والتصنيفات للأدمن. ليست نفس شاشة الاستعراض.

إنشاء الحجز داخل `/demo` محاكاة داخل ذاكرة الصفحة فقط. تحديث الصفحة يمسح التغييرات. تغيير الدور للمعاينة ليس آلية صلاحيات. أسماء العملاء والأرقام والفساتين والإحصاءات تجريبية. الرسومات أصلية مبدئية وليست صور منتجات حقيقية. تاريخ مساحة الاستعراض ثابت: السبت 5 ديسمبر 2026.

## الأدوات المستخدمة

- Next.js App Router وTypeScript.
- Tailwind CSS v4.
- مكونات shadcn/ui فعلية، مبنية على Base UI في الإصدار الذي تم تثبيته.
- Supabase Auth وPostgreSQL وStorage، مع `@supabase/ssr`.
- Zod للتحقق على الخادم، وPlaywright لاختبارات المتصفح.

الإصدارات الدقيقة في `package-lock.json`. استخدم `npm ci` لإعادة نفس التثبيت. لم تُستخدم صور منتجات خارجية.

## ربط مشروع Supabase جديد

1. أنشئ مشروعًا جديدًا تحت حسابك وحدد المنطقة وخطة التكلفة بنفسك. لم تُنشأ موارد مدفوعة بالنيابة عنك.
2. انسخ `.env.example` إلى `.env.local` على جهازك، وأضف عنوان المشروع و**Publishable Key** فقط. لا تضع `service_role` أو مفتاحًا سريًا في أي متغير `NEXT_PUBLIC_`، ولا تشارك كلمة مرور قاعدة البيانات في المحادثات أو Git.
3. نفّذ الملفين داخل `supabase/migrations/` بالترتيب: `202611220001_foundation.sql` ثم `202611220002_inventory.sql`، عبر SQL Editor للمشروع الجديد. لا تطبقه على مشروع قائم دون مراجعة: يضبط منح الوصول داخل `public` ويحتاج صلاحيات مالك القاعدة.
4. عطّل التسجيل العام من إعدادات Supabase Auth. أنشئ أول حساب أدمن من لوحة Authentication، ثم أضف سجل `profiles` المطابق لمعرف حسابه، من SQL Editor فقط:

```sql
-- استبدل المعرف بمعرف الحساب الحقيقي من لوحة Authentication.
insert into public.profiles(id, full_name, role)
values ('AUTH_USER_UUID_HERE', 'اسم المدير', 'admin');
```

5. حسابات الموظفين تُنشأ حاليًا من لوحة Authentication ثم يضاف لها سجل `profiles` بالدور `employee`. واجهة إدارة المستخدمين لم تُنفذ بعد. اجعل `active=false` لتعطيل الموظف بدل حذف سجله التاريخي.
6. أعد تشغيل التطبيق. ادخل من `/login`، وأضف تصنيفًا ثم فستانًا من `/workspace`. يبدأ الفستان بحالة غير متاح. افتح اسم الفستان من المخزون لتحريره ورفع صوره، وراجع رابط الأرشيف لاستعادة فستان مؤرشف.
7. تأكد من اختبار الصلاحيات بحساب أدمن وموظف وزائر على مشروع اختبار، خصوصًا Auth وStorage في الخدمة الحقيقية. اختبارات PostgreSQL المحلية لا تثبت تكامل الخدمة المُستضافة.

الـ Storage bucket المسمى `dress-images` متاح لصور الكتالوج برابط مباشر. لا ترفع فيه أي هوية أو بيانات عميل أو مستند خاص. رفع الصور محصور بالأدمن على مستوى RLS. أرشفة فستان لا تسحب صورة سبق نشر رابطها من كاش أو من شخص احتفظ بالرابط. واجهة رفع الصور متاحة للأدمن بعد الربط. تتحقق من الملف وتعيد ترميزه WebP وتزيل EXIF. حذف الصور وترتيبها يدويًا لم يُنفذا بعد.

## السياسات غير المحسومة

كل التغييرات المالية والتشغيلية داخل العرض غير حقيقية. إنشاء الحجوزات الفعلية في قاعدة البيانات متوقف افتراضيًا عبر `settings.live_bookings_enabled=false`، وتحتاج حقول السياسة إلى اعتماد صريح. **لا تغيّرها لمجرد تشغيل العرض**.

راجع `docs/DECISIONS.md` قبل التشغيل. لم نفعّل الاحتفاظ بالبطاقة الشخصية، ولم نخزن رقمًا أو صورة لهوية. الإلغاء والاسترداد وتعديل السعر/التاريخ والتسليم والاستلام تحتاج قرارات وتنفيذًا لاحقًا.

يوجد RPC تأسيسي لإنشاء الحجز ودفعة المقدم في معاملة واحدة، وRPC لتسجيل دفعة لاحقة. لم تُوصل تلك الوظائف بواجهة الإنتاج بعد. لا يوجد دفع إلكتروني أو ربط ببوابة تحصيل.

## الاختبارات

```bash
npm run lint
npm run typecheck
npm test
npm run test:db
npm run build
npm run test:e2e
```

- `npm test`: اختبارات قاعدة يوم التجهيز، أول موعد لاحق، التواريخ وحساب القروش دون أخطاء الكسور العائمة.
- `npm run test:db`: يشغّل PostgreSQL مؤقتًا على المنفذ 55439 باستخدام `embedded-postgres`، ثم يختبر المهاجرة وRLS والمعاملات. لا يتصل بأي مشروع سحابي. schemas الخاصة بـ Auth وStorage ممثلة محليًا، وليست خدمة Supabase الحقيقية. يتطلب السماح بتثبيت حزمة PostgreSQL الأصلية لنظامك، وتشغيله كمستخدم غير root.
- `npm run test:e2e`: بعد `build`، يشغّل التطبيق ويختبره في Chrome. على Linux يستخدم `/usr/bin/google-chrome` افتراضيًا. يمكنك ضبط `CHROME_PATH`، أو تعديل `playwright.config.ts` لاستخدام Chromium المثبت عبر Playwright.
- صور المعاينة الفعلية في `evidence/`. تقرير التحقق في `docs/VERIFICATION.md`.

## الأمان في هذه المرحلة

- السعر الاسترشادي في جدول منفصل `dress_prices`، وليس عمودًا مخفيًا بالواجهة فقط.
- الزائر لا يملك الوصول إلى العملاء والحجوزات والمدفوعات والسجل.
- الموظف يرى الحجوزات التي أنشأها أو أُسندت له فقط. هذا قيد احترازي مؤقت حتى اعتماد نطاق عمل الموظفين، وليس قرارًا نهائيًا عن طريقة تشغيل الأتيليه.
- لا يستطيع المستخدم تعديل دوره. قراءة السعر الإداري والمالية العامة وسجل النشاط للأدمن فقط.
- منع التعارض في PostgreSQL بقيد `EXCLUDE`، وليس بفحص واجهة فقط.
- المدفوعات بالقروش الصحيحة، لا يُقبل دفع يتجاوز المستحق، ولا يوجد حذف مباشر للدفعات أو السجل عبر أدوار التطبيق.
- قيود قاعدة البيانات لا تعني أن اختبارات الأمان الكاملة انتهت. مطلوب اختبار اختراق وصلاحيات على Supabase قبل الإنتاج.

## ما يأتي بعد هذه الحزمة

راجع `docs/IMPLEMENTATION.md` للتفريق بين المنفذ، والتجريبي، وغير المنفذ. أهم المراحل التالية: اعتماد السياسات، إنشاء وربط بيئة اختبار، استكمال حذف الصور وترتيبها وإدارة التصنيفات، إدارة الموظفين، ربط الحجوزات والمدفوعات الفعلية، التسليم والاستلام والفحص، التنبيهات المشتقة من الواقع، تقارير مالية حقيقية وتصدير آمن، النسخ الاحتياطي وتجربة الاستعادة، ثم النشر على Vercel تحت حساب المالك.

اسم الأتيليه والألوان والرسومات كلها اختيارات مبدئية قابلة للتغيير. لا يوجد حجز ذاتي للزائر، أو QR، أو تأمين مالي، أو نظام صيانة مستقل.

## تحديث 0.3.0

شاشات قراءة حقيقية محمية لسجل النشاط والفريق والعملاء وتاريخ حجوزات العميل للأدمن، وتفاصيل الحجز ودفعاته ضمن صلاحيات الحساب. قائمة العملاء والسجل المجمّع للأدمن فقط؛ الموظف يرى بيانات العميل داخل الحجز المصرح له به. عرض التوقيت في السجل والدفعات UTC، ولا يتم توليد تنبيهات تشغيلية من منطقة زمنية مفترضة. لا توجد مهاجرة جديدة بعد ملفي 0.2.0.
